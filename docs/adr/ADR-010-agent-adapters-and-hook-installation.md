# ADR-010: Agent adapters, hook forwarder and hook installation

- **Status:** Accepted (Sprint 02)
- **Date:** 2026-11-05
- **Owner:** Implementation lead
- **Related:** ADR-008 (event contract), ADR-009 (IPC), `docs/adapters/CLAUDE_CODE.md`

## Context

Lullshift observes agents through the hooks they offer. Hooks run inside the agent's process tree with the user's permissions, and a misbehaving hook can block or steer the agent (for example, exit code 2 blocks an action; stdout from some hooks becomes model context). Editing an agent's settings is sensitive user configuration (CLAUDE.md rule 5).

## Decision

### Forwarder: the Lullshift executable in hook mode

- The installed hook command is the Lullshift executable itself, `lullshift-desktop hook <adapter> --data-dir <dir>`. Hook mode never starts the app UI. This avoids packaging a second binary and its path drifting from the app.
- **Zero-effect contract:** hook mode always exits 0, writes nothing to stdout or stderr, and exits 0 even on panic (panic hook). It reads at most 1 MiB of stdin and finishes within 2 seconds in all cases. Events the app would reject are dropped locally.
- Hooks are registered in **exec form** (no shell) with `async: true`, so the agent never waits for Lullshift.
- The event time is taken when the hook process starts, before stdin is read, so separate hook processes keep the order in which the agent ran them.
- Each hook run gets a fresh random `eventId`. Duplicate protection for users comes from state: notifications fire only when a session changes into `needs_attention`, and at most once per session in 15 seconds. That window covers a `working` event landing between a permission request and Claude Code's permission notification.
- Only enum-like hints are forwarded; prompts, messages, tool data, paths and transcripts are never read into Lullshift types. Exception since Sprint 04: when the user opts in to task-context capture, the first prompt and the agent's question text are sent beside the event, cleaned and capped (ADR-013). Tool data, paths and transcripts are still never read.

### Installer

- **Consent first:** install runs only from an explicit action in the app, after a panel that names the exact file, the events and what is and isn't sent. The install commands are granted to the `main` window only; activity webviews must never receive that capability. After the panel, Rust shows a native confirmation dialog that names the settings file, and installs only if the user chooses **Connect** (S03-T07, Sprint 03). A script in a webview therefore can't install hooks on its own.
- **Scope:** Claude Code user settings (`~/.claude/settings.json`, or `$CLAUDE_CONFIG_DIR/settings.json`), so all projects are covered. Project and managed settings are never touched.
- **Safety:**
  - A settings file that isn't a JSON object, or whose `hooks` value isn't an object of arrays, is refused and left untouched.
  - The original bytes are backed up under `<app data>/adapters/claude-code/backups/` before the first change; backups are never deleted automatically.
  - Writes go to a uniquely named temporary file in the same folder, keep the original permissions, are synced, then renamed over the file. They abort if the file changed since it was read. A change made in the instant between that check and the rename is lost; avoiding that needs file locking that Claude Code doesn't use.
  - Symlinked, non-regular and read-only settings files are refused, never replaced. Backups are owner-only on Unix.
  - Key order, every unrelated setting and a UTF-8 byte order mark are preserved. The file is re-serialized, so spacing and formatting may change; the consent panel says so.
- **Idempotent and upgradable:** installing again first removes Lullshift's own handlers (exec-form `lullshift*` executables with `hook claude-code` arguments), then adds current ones: one handler per event.
- **Uninstall:**
  - If the file is byte-identical to what Lullshift last wrote, and has been at every repair since the first install, the original is restored byte for byte (or removed, if it didn't exist). A missing backup falls back to removal.
  - Otherwise only Lullshift's handlers, and the keys Lullshift itself created, are removed; the user's later edits stay.
- **Record:** the undo information (paths, hashes, created keys; never file content) is stored in SQLite (`adapter_installations`, migration 0002) and must be saved for the install to count; if saving fails, the install is undone. Status, repair and uninstall act on the recorded settings path, since the app's environment (`CLAUDE_CONFIG_DIR`) can differ between launches. Without a record, uninstall still removes Lullshift's handlers. Install and uninstall never run concurrently.

### Protocol addition

`session_ended` / `ended` joins the event contract (ADR-008): the provider closed the session without claiming the task was done. It is terminal and distinct from `completed`.

### Windows pipe access (S02-T06, from the Sprint 01 review)

Keep the default pipe DACL for v1. Owner-only access needs either `unsafe` Win32 code or a dependency. The `interprocess` crate's safe security-descriptor API was evaluated: pipe creation failed in our environment (error 123, even without a descriptor), so it wasn't adopted.

Pipe names can be listed by other local users (for example by listing `\\.\pipe\`), so the per-launch random name prevents guessing but not discovery.

The residual risk stays as in ADR-009: other local users can hold connection slots, but they can't authenticate or read events. Revisit if a multi-user deployment needs it.

## Consequences

- An app move or update changes the executable path; the app shows "Needs repair" and offers to update the hooks.
- If Lullshift is removed or moved without disconnecting, Claude Code keeps trying to run a missing executable. The consent panel warns about this; the OS uninstaller now runs the same cleanup (S11-T06, see the implementation notes below). Manual cleanup: delete the handlers whose `args` start with `hook`, `claude-code` from the settings file.
- Sessions in folders Claude Code hasn't trusted send nothing (Claude Code holds hooks back), and interrupts send no event. The UI shows these sessions as stale, not as finished.
- Every hook run starts a short-lived Lullshift process. Exec form and the 2-second cap keep this cheap.

## Implementation notes: uninstaller cleanup (S11-T06)

- **`lullshift-desktop --uninstall-hooks`** (`apps/desktop/src-tauri/src/uninstall_hooks.rs`) runs the same uninstall functions as Disconnect for Claude Code, Codex and Cursor, with no UI, no stdout or stderr, exit code 0 always, and no new IPC. For each adapter it uses the install record in `lullshift.db` (settings path, backup, created keys), or, without a record, removes only Lullshift's own entries from the default location. It marks the adapter uninstalled and ends tracked sessions, like Disconnect. It never creates a database or a settings file, leaves files that don't parse untouched, keeps the user's own hooks, and a failure for one agent doesn't stop the others. A second run changes nothing.
- **Wiring:** Windows NSIS pre-uninstall hook (`windows/hooks.nsh`, skipped only in `/UPDATE` mode; a reinstall removes the hooks and a post-install step restores them, see the 2026-11-06 review amendment), Linux deb `prerm` (`linux/prerm`, `remove` only, runs per user via `runuser`, never as root). macOS has no uninstaller: disconnect first. AppImage has none either. Details and caveats: `docs/RELEASING.md` section 4.
- **Missing executable:** per the Claude Code hooks documentation, a command hook that can't be started is a non-blocking error (a "hook error" notice, the action proceeds). Only hooks with `onFailure: "block"` block, and Lullshift never sets it; async hooks can't block at all. So a leftover hook is noise, not a failure of Claude Code itself. Codex and Cursor aren't documented; assumed the same (Cursor `failClosed` is never set, Codex hooks are async) and to be confirmed by hand.
- **Tests:** `uninstall_hooks::tests` (temp directories only) cover restore, later user edits, own hooks, missing database, unparsable file, idempotence and database state. `tests/release_config.rs` checks the wiring.

## Amendment (2026-11-06, S12-T05): reinstall and AppImage

- **Windows reinstall keeps the hooks** (owner decision 26.8). *Superseded by the review amendment below for the mechanism; the user-visible result is unchanged.*
- **AppImage hooks point at `$APPIMAGE`** (owner decision 26.7), not the temporary mount, when it is an absolute existing file named `lullshift*` and consistent with `APPDIR`. Applies to Claude Code (exec form `command`) and to the Codex and Cursor command strings. There is still no uninstaller for AppImage: Disconnect first.

## Amendment (2026-11-06, security review M1): reinstall restores hooks instead of keeping them

- **Problem.** The first reinstall rule kept the hooks whenever the uninstaller ran in place (`$EXEDIR == $INSTDIR`). Tauri's installer runs the old uninstaller as `uninstall.exe [/P] _?=<dir>` on the reinstall page, before the folder page. If the user then cancelled, or chose a different folder, the hooks pointed at a deleted program in a user-writable folder: a persistence point (anything placed there later would be run by the agent).
- **Decision.** The NSIS pre-uninstall hook keeps hooks **only for `/UPDATE`** (the updater replaces the program in the same folder). Every other uninstall removes them, as before. To keep owner decision 26.8 (a reinstall keeps the agent connections), `NSIS_HOOK_POSTINSTALL` runs the newly installed program with `--repair-recorded-hooks`, which re-applies hooks for the new program path.
- **Consent.** The stored install record in `lullshift.db` (written by Connect, removed by Disconnect and by a real uninstall) is what keeps the consent. Only an adapter with a record is restored; with no record, or if the database was deleted, nothing is re-applied. The restore uses the normal install code (backup first, atomic write, idempotent, never touches the user's own entries) and writes the new record.
- **How the record survives the removal.** When the uninstaller is run in place by a setup, the hook passes `--keep-records` to `--uninstall-hooks`: hooks removed, records kept, and a marker file `hook-restore.pending` with the time is written in the app data directory (only if a record exists). `--repair-recorded-hooks` does nothing without that marker, so a first install, an in-place update and a normal start never change an agent file. It deletes the marker first (one shot). A marker older than one hour, unreadable or from the future is stale: the records are marked uninstalled and nothing is restored (an uninstall that was cancelled long ago must not bring hooks back on a much later install).
- **Cases.** Uninstall then cancel: no hooks, no program; if a setup finishes within the hour they are restored, otherwise the next run clears the records. Upgrade into another folder: hooks restored to the new path. Settings > Apps uninstall: hooks and records removed, no marker. If `$EXEDIR` is misjudged, the failure is "records deleted, nothing restored", never a hook left behind. Linux `.deb`: unchanged (`prerm` on `remove` only, `postinst` does nothing).
- **Implementation.** `apps/desktop/src-tauri/src/repair_hooks.rs` (new, mirrors `uninstall_hooks.rs`), `windows/hooks.nsh`, `main.rs` dispatch, tests in `repair_hooks::tests` and `uninstall_hooks::tests` against temp directories with fake records, wiring checked by `tests/release_config.rs`. Details and manual checks: `docs/RELEASING.md` section 4.
- **Related (review L1).** `--uninstall-hooks` removes only entries whose command names this app's data directory (a second build keeps its own); see ADR-021.

## Amendment (2026-11-07, decision 33): packaged apps, stale connection files and the failure marker

- **Problem.** On Windows, a program started from inside an MSIX or Store app (for example a terminal in the Claude desktop app) inherits that app's package identity. Windows redirects its AppData writes into a private copy, `%LOCALAPPDATA%\Packages\<family>\LocalCache\Roaming\...`, and its reads fall through to the real AppData only when no private copy exists. Lullshift started that way once left `ipc\endpoint.json` and `ipc\token` in Claude's private copy. Later, with Lullshift running normally, Claude Code sessions inside the Claude app read those old copies: their events went to a pipe that no longer existed, then were refused for a token mismatch. The hook is silent by design, so nothing explained it.
- **Packaged-context detection.** At run time the app asks Windows `GetCurrentPackageFamilyName` (kernel32, Windows 8+). Success means Lullshift itself runs inside a package; Sessions and Integrations then show a persistent warning naming the package ("started from inside another app (Claude) ... quit and start Lullshift from the Start menu or File Explorer"). Nothing is blocked. The call lives in a new crate, `crates/windows-package` (`windows-sys` `=0.61.2`, already in the lockfile), which is the second crate besides `macos-webrtc` allowed to use `unsafe`; the lint guard in `apps/desktop/src-tauri/src/webrtc.rs` names both. Other platforms compile it to `None`.
- **Scanning other packages for our own two files.** When Lullshift is *not* packaged, `connection_health` looks at `%LOCALAPPDATA%\Packages\<family>\LocalCache\Roaming\<data dir name>\ipc\` for exactly `endpoint.json` and `token`. The data dir name is the last component of Tauri's `app_data_dir()`, the same source the app uses. A copy is stale when its content (trimmed) differs from the real file, or the real file is missing; the comparison is in memory and no content is logged or returned (the UI only learns "address" or "access key"). Every directory on the path is checked with `symlink_metadata` and refused if it is a reparse point (symlink, junction, mount point: `FILE_ATTRIBUTE_REPARSE_POINT`). Each file is then opened by handle without following a reparse point at the file itself (`FILE_FLAG_OPEN_REPARSE_POINT`); through that handle it must be a regular file of at most 16 KiB whose final path (`GetFinalPathNameByHandleW`, normalized, compared case-insensitively) is exactly the expected path built on the canonical Packages folder, so a junction anywhere on the way is refused even if it appeared after the directory checks. Contents are read through that handle into zeroized buffers and compared in constant time. At most 2,000 package folders and 3 seconds per scan; past either the result says "partial". Family names must be 1 to 128 of `[A-Za-z0-9._-]`, must not start or end with a dot (Windows drops a trailing dot) and must not be a reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9`, any case, with or without an extension). Nothing else in the package is read, in particular not the private database copy.
- **User-initiated deletion only.** Integrations shows one card per package with stale copies and a **Fix** button. `connection_fix_stale(family)` re-validates the family name, requires it in a fresh listing of the Packages folder (exact spelling), re-checks every directory on the path, opens each file by checked handle as above, compares its content through that handle, and deletes only a still-stale file through that same handle (`SetFileInformationByHandle` with `FileDispositionInfoEx` and POSIX semantics, falling back to `FileDispositionInfo`). Fix calls are serialised. It reports deleted, already current and failed files. It is refused while Lullshift is itself packaged and outside Windows. Nothing deletes automatically. The text says sessions already open may need their next event or a restart, and that data from runs inside that app stays where it is. Because the delete goes through the handle whose final path was checked, swapping a directory for a junction after the checks can no longer redirect it to a same-named file elsewhere (security review M1; a Windows test swaps `ipc` for a junction to a victim folder and the victim's files survive). Package names shown in the UI are folder names under the user's own `Packages` folder, which any process of that user can create, so a name is a hint, not proof of which app it is (review L8, accepted): the worst a fake folder can do is get its own copies of our two files deleted after the user presses Fix.
- **Failure marker (data-free).** In hook mode, when the app refuses the token (`Unauthorized`) or the exchange fails while `endpoint.json` exists, the forwarder writes `<data-dir>\ipc\last-hook-failure.json` = `{"adapter","reason":"rejected"|"unreachable","utc"}` and nothing else: no session id, task data or paths. It is written atomically (a temporary file with a unique name from the process id and random bytes, created new and, on Windows, opened without following a reparse point, then renamed; removed on error), is under 512 bytes, is not rewritten for the same adapter and reason within 60 seconds, never creates the `ipc` directory and ignores every error. The zero-effect contract is unchanged: exit 0, no stdout or stderr, inside the existing 2-second deadline: the send budget is counted from process start and keeps 250 ms for the marker, and with under 50 ms left nothing is sent or recorded. Inside a package the write lands in the package's private copy, which is why the app reads markers from the real data dir and from the package copies found by the scan, with the same path rules. The app parses markers strictly (size cap, exact fields, known adapter ids, reason enum, RFC 3339 time 2020 to 2200) and shows one only if it was written during this run of the app, is not more than 5 minutes in the future, and is later than the last event received from that adapter (for the real data folder) or the last Fix of that package (for a package's copy: the app can't tell whether an event came from inside a package, so a success from elsewhere must not hide that package's failure). A failure while Lullshift was closed is expected and not shown.
- **Implementation.** `crates/windows-package`, `crates/agent-adapters/src/hook_failure.rs` and `forward.rs`, `apps/desktop/src-tauri/src/packaged.rs` (commands `packaged_context`, `connection_health`, `connection_fix_stale`; `connection_fix_stale` is listed with the main-window-only sensitive permissions), `apps/desktop/src/connection.ts` and `ConnectionProblems.tsx`. `windows-package` holds exactly five `unsafe` blocks (two for the package name, one for the final path, two for the delete), denies undocumented ones, and the lint guard in `webrtc.rs` counts them. Tests: scanning, staleness, junction refusal (created with `mklink /J`), a junction swapped in before the delete, the fresh-listing and name rules, Fix re-validation and the private database being left alone in `packaged::tests`; marker write, rate limit, concurrent writers and strict parsing in `hook_failure::tests`; marker on an old address and on a refused token in `forward::tests`; the real executable in hook mode still exits 0 silently in `apps/desktop/src-tauri/tests/hook_zero_output.rs`. Manual check: M12-16.

## Amendment (2026-11-07, decision 35, ADR-025): the hook also sends the agent's process

The forwarder now looks up the agent's process (the first non-shell ancestor of the hook process, with a start key, read-only) and sends it as an optional `process` field beside the event, so the app can notice later that the process is gone. The zero-effect contract is unchanged: exit 0, nothing on stdout or stderr, inside the same 2 s deadline (the lookup runs before the send, on the same deadline thread), and any failure means the event goes without a process. An older app that rejects the unknown field gets the event again without it. The hook never signals or otherwise acts on a process. See ADR-025.
